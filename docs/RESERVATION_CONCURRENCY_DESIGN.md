# Reservation concurrency design

Checkpoint 6.0 compared the approaches below. Checkpoint 6.1 implements option A in `AvailabilityTransactions` and `AvailabilityRepository`. Rowversion protects edits, and SQL overlap queries seek the existing tenant/property range indexes to avoid scanning unrelated uncommitted rows. See [availability engine](AVAILABILITY_ENGINE.md).

| Concern | A. Transaction-owned application lock | B. Unique occupied-night table | C. Serializable interval reads |
| --- | --- | --- | --- |
| All three conflict pairs | One exclusive tenant/property lock and queries across reservations and blocks | All active nights from both sources share a unique tenant/property/date key | Both tables need indexed key-range reads, consistent predicates and lock order, including empty ranges |
| Concurrent inserts and edits | Serialize per property and recheck under lock. RowVersion rejects stale edits. | Competing inserts hit uniqueness. Changes replace occupancy rows atomically. RowVersion still protects edits. | Range locks prevent phantoms. Overlap reads followed by inserts can deadlock. Correctness depends on predicates, plans and transactional discipline. |
| Cancellation and release | Update hold state or release boundary under same lock | Delete only released projection rows. Keep booking and historical nights. | Update both relevant read ranges consistently, using the same locking order as creation |
| Property moves | Lock both tenant/property keys in deterministic order and reload after both locks | Move all affected projection rows in one transaction, in consistent key order | Acquire ranges for both properties and sources. Lock footprint and deadlock risk increase. |
| Rollback and recovery | Lock ends with commit/rollback. Booking, nights and audit roll back together. | Projection and authoritative records roll back together | SQL transaction releases range locks on commit/rollback |
| Deadlocks and timeouts | Bounded wait, stable lock order, explicit rollback on negative lock result. SQL deadlocks still possible. | Unique collisions and row/key-order deadlocks must be distinguished | Deadlock handling and plan regressions require deliberate testing |
| Isolation and maintenance | Canonical organization/property key, one SQL database, existing indexes. Every writer must follow protocol. | Composite uniqueness and FK, durable projection, one write per night and reconciliation cost | Tenant-leading indexes required. Plan-dependent range size and cross-source ordering are harder to maintain. |

Option A fits existing reservation and block tables and avoids a second occupancy projection. B is a viable fallback if a later independent writer requires database-enforced per-night uniqueness. C is viable with careful SQL and database tests, but the two independent interval tables make its locking more complex. Rowversion detects updates to the same row. It cannot prevent two distinct overlapping inserts.

## Write protocol

1. Resolve the authenticated tenant and authorize the requested operation. For updates read the original scope/property and requested destination, then begin a fresh SQL transaction at Read Committed. Do not take an earlier transaction snapshot for authoritative overlap reads.
2. Acquire an exclusive transaction-owned `sp_getapplock` on `hostgrid:availability:{org-guid-N}:{property-guid-N}` under the `public` database principal. Use the actual EF transaction and connection with parameters. For moves deduplicate and sort property GUIDs before acquiring the locks. Commit or roll back to release ownership. Configure `Availability:LockTimeoutMilliseconds` from 1 to 15,000 ms, default 5,000. [Microsoft SQL Server application lock documentation](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/sp-getapplock-transact-sql)
3. Reload the authoritative records after locking. Recheck membership/resource scope, original property, current expected RowVersion and capacity. If the row moved before acquisition, fail stale or restart from the beginning after rollback. Keep property eligibility rules in one service. Property status and capacity updates that affect booking admission must participate in this protocol or have a separate, tested atomic guard. Any future commission-schedule read/write serialization should follow an agreed consistent lock order.
4. Test the requested half-open interval against all blocking reservations and active blocks in the authorized tenant/property. Exclude the edited ID only in its own table. Apply approved release bounds before overlap evaluation. Use bounded reads for previews. All creates, date edits, moves, block activation/deactivation, cancellations, lifecycle actions with availability impact, and manual releases follow the same protocol. Add an explicit handoff for future maintenance and Owner request approvals.
5. Write the reservation or block and audit in the transaction. Future nightly/history operations join that boundary. Keep external calls outside it. Treat real overlap and stale rowversion as distinct conflict codes. Results 0 and 1 indicate lock acquisition. Negative results include timeout (-1), cancellation (-2), deadlock (-3) and invalid invocation (-999), and all abort the unit. Map transient failures to safe 503 responses. The EF execution strategy wraps the entire unit and can replay a known precommit failure. Clear tracked state on failure, use stable IDs across attempts, and mark interrupted commit outcomes as uncertain without replay. [SQL Server locking and row versioning](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-transaction-locking-and-row-versioning-guide)

## SQL Server acceptance gate

Use separate contexts and connections against an isolated SQL Server fixture. Synchronize the competing operations and prove exactly one successful commit and one conflict for overlapping reservation/reservation, reservation/block in both orders, and block/block. Prove same-day adjacency and disjoint properties/tenants succeed. Cover self-exclusion, stale edits, deterministic two-property moves, edit/create and release/create race ordering, a failed mutation leaving every row and audit unchanged, and reacquisition after rollback, timeout or deadlock. Verify a lock on one tenant/property does not serialize independent scopes and record no sensitive details in conflicts. Fixture-seed statuses to test pure hold rules approved for 6.1. Later checkpoints repeat these guarantees through the public endpoints.

The final 6.1 suite passed **64 of 64**. The five paired write cases covered reservation/reservation, reservation/block in both orders, block/block and edit/edit. Each case held the first write open until the competing request reached the lock command, then asserted one successful write, one conflict and exactly one remaining interval in the contested range. Another race committed the release before the waiting hold took the released dates. Independent-property, status and capacity races, opposite Pending moves, lock timeout, caller cancellation and rollback passed. A precommit injected SQL error exercised EF's retry strategy and acquired the property lock twice, with exactly one final hold and audit. Deadlock return codes are handled explicitly. The suite exercised retries via an injected transient SQL error.
