# Historical reservations

Use the separate **Historical entry** action for completed stays. Require an Active property, current capacity compliance, original contractual dates, actual historical confirmation date, recorded amounts, a reason and private PDF evidence that meets the existing scan policy. Optional actual dates stay as date-only evidence. The API can record an exact arrival alone or an ordered arrival and departure pair, which must agree with any supplied dates. If only an actual departure date is known, use the date-only field. The system records its own entry time separately and leaves unknown confirmation or actual stay times unset.

Historical entries use the provided confirmation date for CommissionRateHistory, without a default or substitute date. The same SQL property lock enforces historical overlap and calendar block checks. A closed financial period rejects entry. The booking is recorded as CheckedOut with no invented payment.

`POST /api/v1/organizations/{organizationId}/reservations/historical` accepts multipart `request` JSON and `file` PDF. The API authorizes before staging. Blob storage precedes the SQL transaction, and metadata, the booking, pricing and audit commit together in SQL. A known rollback removes the staged blob. If commit outcome is uncertain, private content is retained for reconciliation. `GET /reservations/{id}/evidence` within the same organization prefix rechecks booking permissions and scan state. The evidence is not a property document and is invisible to the Owner portal. Production requires a working scanner. The existing Development-only private quarantine preview setting remains available for fictitious verification.
